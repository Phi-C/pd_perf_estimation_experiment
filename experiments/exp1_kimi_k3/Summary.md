## Prefill

Profiling 段（切完 warmup）：4,305 个 forward、2,472 请求，ISL 320.76 M token（fresh 13.89 M，prefix 命中 95.67%）。下面主报 **ISL tok/s**。

这段 wall time 只做三件事。以 **trace 窗口 3,602 s** 为同一套分母：

| 成分 | 秒 | 占比 | 怎么来的 | 是什么 |
|---|---:|---:|---|---|
| 纯模型 forward | 1,566 | 43.5% | **实测 + 外推**。HIP event 量 `run_model` 得 Σ`fwd_gpu_ms` = 1,034.8 s，但点表只覆盖 66.1% 的 ISL，按覆盖率放大到全量：1,034.8 / 0.661 | GPU 真正在算的时间 |
| 其它开销 | 579 | 16.1% | **残差，无埋点**。`3,602 − 1,566 − 1,457` 倒减出来的 | 调度、`prepare_inputs`、KV offload、sampling 等 step 内非模型开销 |
| 空转 | 1,457 | 40.4% | **实测，且是保守下界**。`idle_gaps.json`，只记 running + waiting 两个队列都空的段，时长保守折算 | 引擎无事可做，在等下一条请求（agent 思考 / 工具往返） |
| 合计 | 3,602 | 100% | **直读**。trace 窗口 | |

三行的可信度不同，用它们时要记住：

- **579 不是测出来的**，是倒减的残差，因此外推的误差全落在它身上 —— 1,566 若高估，579 就等量低估，反之亦然。
- 只有 1,457 和 3,602 是不依赖外推的直读量。

四种吞吐 = 分母里**留哪些成分**（不是一条直线，是 2×2）：

| 口径 | 分母里留下 | 分母 (s) | ISL tok/s | 回答什么 |
|---|---|---:|---:|---|
| 实际交付 | 模型 + 其它开销 + 空转 | 3,602 | **89,051** | 这段 trace 墙上实际跑到多少 |
| 剔空转 | 模型 + 其它开销 | 2,145 | **≥ 149,538** | 只要队列不空，当前引擎有多快 |
| 剔其它开销 | 模型 + 空转 | 3,023 | **≤ 106,124** | 调度/后处理与 GPU 完美 overlap，但空转还在 |
| 纯模型上界 | 只留模型 | 1,566 | **204,892** | -  |

```text
                         剔其它开销、留空转
                    ---------------------->  ≤106,124
                   /                           \
     89,051  -----                                ---->  204,892
                   \                           /
                    ---------------------->  ≥149,538
                         剔空转、留其它开销
```

**怎么读。** 空转是 workload 带来的（不是引擎低效），所以「剔其它开销、留空转」才是「调度优化完、负载形态不变」时更该看的数；多路会话交错会填掉一部分空转，这个数会往纯模型靠。空转 1,457 s 是下界，所以「剔空转」是吞吐下界、「留空转」是吞吐上界。自洽：`3,602 − 1,457 = 2,145`。

**不要和表外两个数直接相除。**

- CI / aiperf 报的交付吞吐是 <span style="color:red"><strong>81,619</strong></span>（分母 **3,930 s**，不是表里的 3,602 s）。3,930 s = 信用窗口关掉后，再等到**已经发出的请求全部跑完**（尾部排空）。窗口内不再发新请求，但本例最长 request latency 约 823 s，排空大约 300 s，这段时间几乎没有新的 prefill forward，客户端却还在收 completion，AIPerf 仍把它算进 \(T\)。同一套 ISL：`320.76M / 3602 = 89,051`（上表），`320.76M / 3930 = 81,619`（CI）。

- 点表只给 3,400/4,305 个 forward 标了单价。纯模型若**不外推**（分子分母都缩到覆盖内）是 ISL **204,801** / fresh **10,066**；上表 204,892 是外推全量。

方法细节见 [`prefill/SKILL.md`](../../prefill/SKILL.md) 第 ⑤ 节。

## Decode

Profiling 段：113,439 个 forward、2,451 请求，Σ output token **2,247,264**（重放口径；每请求 OSL 917）。batch size 中位 20、均值 19.81。下面主报 **output tok/s**。

同样把 wall time 只做三件事。以 **aiperf 窗口 3,684 s** 为同一套分母：

| 成分 | 秒 | 占比 | 怎么来的 | 是什么 |
|---|---:|---:|---|---|
| 纯模型 forward | 3,487.6 | 94.7% | **实测 + 外推**。149 点点表命中 82,543/113,439 forward（token 覆盖 80.2%），Σ`fwd_gpu_ms` = 2,595.2 s；未命中的按波量化模型 `D ≈ f(⌈b/16⌉)` 补到全覆盖 | GPU 真正在算的时间 |
| 其它开销 | 24.7 | 0.7% | **两条埋点相减，不是残差**。Σ`D_ms` − Σ`fwd_gpu_ms` = 3,512.3 − 3,487.6 | 调度、sampling 等 step 内非模型开销（约 0.20–0.22 ms/step） |
| 空转 | 171.7 | 4.7% | **残差，无埋点**。`3,684 − 3,512.3` 倒减出来的。decode 侧没有 `idle_gaps.json` 的对应物，原因见下 | forward 之间引擎没活干 |
| 合计 | 3,684 | 100% | **直读**。aiperf 窗口 | |

和 prefill **残差落在相反的行**：prefill 空转是实测下界、其它开销是倒减；decode 其它开销是埋点相减、空转是倒减。因此 171.7 s 吃掉窗口边界和重放偏差，不要单独引用；3,487.6 依赖外推，但波量化经 149 点验证（波内极差 ≤ 6.5%，三波带不重叠），比 prefill 那次外推有独立依据。


四种吞吐 = 分母里**留哪些成分**（同样是 2×2，不是一条直线）：

| 口径 | 分母里留下 | 分母 (s) | output tok/s | 回答什么 |
|---|---|---:|---:|---|
| 实际交付 | 模型 + 其它开销 + 空转 | 3,684 | **610** | 这段墙上实际跑到多少 |
| 剔空转 | 模型 + 其它开销 | 3,512 | **640** | 只要在跑 step，当前引擎有多快 |
| 剔其它开销 | 模型 + 空转 | 3,659 | **614** | 调度/采样与 GPU 完美 overlap，但空转还在 |
| 纯模型上界 | 只留模型 | 3,488 | **644** | - |

```text
                         剔其它开销、留空转
                    ---------------------->  614
                   /                           \
       610  -----                                ---->  644
                   \                           /
                    ---------------------->  640
                         剔空转、留其它开销
```

「剔空转」= `2,247,264 / 3,512.3 = 640`，与把 Σ`D_ms` 当分子分母的算法落在同一点，2×2 自洽。整张表只有 **5.6%**（610 → 644）：decode 已经跑在纯模型时间的 **94.7%** 上。调 step 内调度/sampling 几乎没空间（其它开销 0.7%）。

**和 prefill 比（只比能比的）。**

| | prefill | decode | 能否直接比 |
|---|---:|---:|---|
| 空转占窗口 | **≥ 40.4%** | **≤ 4.7%** | **能，且偏保守**（下界对上界，真实差距更大） |
| 其它开销 | ≤ 16.1% | **0.7%** | **不能** —— prefill 的 579 s 是残差，还含「队列非空但没在跑」的间隙；decode 的 24.7 s 只含 step 内 |
| <mark>实际交付 → 纯模型</mark> | <mark>**2.30x**（89,051 → 204,892）</mark> | <mark>**1.056x**（610 → 644）</mark> | <mark>**能** —— 两边都是同窗口、全覆盖</mark> |

真正的杠杆不在这张 2×2 里，而在 **b 的分布**。这条 trace 按 b 加权纯模型是 644；把 batch 钉在波尾，b=32 单点实测约 **1,012** tok/s（1016.3 / 1013.6 / 1010.8 / 1008.8）。24.1% 的 forward 落在波 1（b ≤ 16），只出 13.2% 的 token，却付整波固定代价。根因是 MoE 专家权重流式读取支配 decode：b 砍一半，step 只从 31.95 ms 降到 27.17 ms（−15%）。**1,012 换的是负载形态，不能拿 1012/644 当「调度优化空间」。**

**不要和表外的数直接相除。**

- CI / aiperf 报 <span style="color:red"><strong>599</strong></span>，和上表 **同一个 3,684 s 窗口**，差在分子：重放 forward 数是上界，Σoutput 2,247,264 vs aiperf 2,206,436（+1.85%）。四行统一用重放分子，比值用 610 → 644。
- 纯模型**不外推**（token 覆盖 80.2%）是 **694**，比全覆盖 644 高 7.8%：未命中形状偏小 b，补上后总吞吐下降。与 prefill 相反——那边报子集 204,801，decode 建议报全覆盖 644（有波模型）。最弱一环是波 3：实测只有 b=33 三个点，trace 里 b=34–37 也按波 3 定价（2.2% token）。

### Analysis

对比纯模型上界吞吐(644)和实际交付吞吐(610), 可以回答：**在这条 trace 已经形成的 batch 形状下**，把空转和 step 内杂活剔掉还能快多少。它没有问：如果每一步的 `b` 长成别的样子，同样的 GPU 能吐多少。杠杆在后者。

一步 decode 的吞吐是 `b / D`，不是「GPU 有多忙」。一步同时有 `b` 条请求、每条出 1 token，墙钟 `D`。644 是把 113,439 步各自的 `b` 和对应的 `D` 加总再相除（分子 Σ`b` = 2,247,264，分母纯模型 3,488 s）——**这条负载的加权平均**，不是硬件峰值。

在这套实验上 `D` 不随 `b` 光滑变，而是按 16 条一波上台阶。波内 `D` 几乎常数，吞吐就几乎随 `b` 线性涨：同样付 ~32 ms，`b=17` 只出 17 个 token（~540 tok/s），`b=32` 出 32 个（~1012 tok/s）。再挤进同一波的请求几乎白捡；刚跨进下一波、人还没凑满则亏——付了更贵的 `D`，`b` 却还小。这个可能和`decode阶段memory-bound`和`compute tile量化`有关。

**1012 不是这条 CI trace 里测到的吞吐**，而是微基准上固定 `b=32`（波 2 波尾）时的 `b / D`。四个点、32 条同构 packed、KV 已灌满：

| 点 | L | D_ms | `32 / D × 1000` |
|---|---:|---:|---:|
| `p49_L147456_b32` | 147,456 | 31.488 | 1016.3 |
| `p38_L172032_b32` | 172,032 | 31.571 | 1013.6 |
| `p120_L155648_b32` | 155,648 | 31.658 | 1010.8 |
| `p73_L163840_b32` | 163,840 | 31.721 | 1008.8 |

均值约 **1,012**。L 从 147k 到 172k 几乎不动，峰值由「装满 32 条」决定。

这条 CI trace 的 `b` 长得不好，所以加权只有 644：中位 20、均值 19.81，落在波 2 前半而不是波尾；24.1% 的 forward 掉进波 1（`b ≤ 16`），仍付整波 1 的固定 `D`（~27 ms），却只贡献 13.2% 的 token。

前面表格中的几个吞吐数据都是在**batch 形状不变**的条件下，压 step 内开销和空转，上限就是 644（+5.6%）。要从 644 走到 1012，必须让每一步的 `b` 都钉在波尾（16 或 32）——改的是**并发从哪来、请求如何凑批**，不是给现有 scheduler 做减法。CI 这条负载给不出那么多同时活着的 decode 请求。**1012 换的是作业，不能当调度优化空间。**

## PD ratio match

Prefill 报 ISL tok/s、decode 报 output tok/s，量纲不同，不能直接相除。稳态下每条请求必须被 prefill 一次、decode 一次，所以配平的是**每节点请求速率** `r`（req/s）：

```
N_P · r_P = N_D · r_D    ⇒    N_D / N_P = r_P / r_D
r_P = T_P / (ISL / req)     r_D = T_D / (OSL / req)
```

本 case profiling 段：ISL/req = 320.76 M / 2,472 = **129,757**；OSL/req = 2,247,264 / 2,451 = **917**。`T_P`、`T_D` 取上面两节已经算过的吞吐，代入即得配比。

五个工作点：

| 工作点 | T_P (ISL tok/s) | T_D (output tok/s) | r_P | r_D | N_P : N_D | 能不能用 |
|---|---:|---:|---:|---:|---|---|
| 实际交付 | 81,619（CI） | 610（重放） | 0.629 | 0.665 | **1 : 0.95** | 交叉验证：贴近部署的 1P1D |
| 两侧纯模型天花板 | 204,892 | 644 | 1.578 | 0.702 | 1 : 2.25～2.55 | **不能用**（循环依赖） |
| prefill 打满 + decode 钉 b=32 | 204,892 | **1,012** | 1.578 | 1.104 | **1 : 1.43** | **能用**，条件是每 decode 节点并发维持 32 |
| prefill 留空转 + decode 钉 b=32 | ≤106,124 | 1,012 | 0.818 | 1.104 | **1 : 0.74** | agent 负载剔不掉空转时用 |
| prefill 留空转 + decode 不钉 b=32 | ≤106,124 | 644 | 0.818 | 0.702 | **1 : 1.17** | 这条到达模式 × 这条 `b` 分布；`T_D` 仍随 `b` 变 |

**钉 b=32 的 `T_D = 1,012` 怎么估。** 不是把本 trace 每步的 `b` 改写成 32 再重放，也不是 644 × 32/20。做法：在微基准上构造同构 packed batch（32 条请求同一 `L`、KV 已灌满、步步都是 `b=32`），探针量每步 `D_ms`（`step_period_ms` 中位数），吞吐 `T_D = b / D = 32 / D_ms × 1000`。四个点（`p49` / `p38` / `p120` / `p73`，L = 147k–172k）分别是 1016.3 / 1013.6 / 1010.8 / 1008.8，均值 **1,012**。L 几乎不动 `D`（31.49–31.72 ms），所以配比里用这一个数。再除以本 case 的 OSL/req：`r_D = 1,012 / 917 = 1.104` req/s。644 仍是 CI 上 Σ`b` / Σ`D`（中位 `b=20`）；钉 b=32 换的是负载形态，点表见上面 Analysis。

**1 : 0.95 只用来验口径。** 两边分子分母配套，才会贴近已部署的 1P1D；若这里离 1 很远，说明前面某处串了。

**两侧天花板 1 : 2.25 不能当部署建议。** 含义本身没算错：一个打满的 prefill 每秒吐出 1.578 条已预填请求，一个跑在本 trace 加权 644 上的 decode 每秒只吃 0.702 条，形式上要 2.25 个 decode 才跟得上。但 `T_D = 644` 是按**这条 trace 的 `b` 分布**加权的，而 `b` 恰恰是配比的**结果**。按 1 : 2.25 加节点后，每节点并发降到约 1/2.25，中位 `b` 从 20 掉到 9、掉进波 1，644 这个输入当场失效。用实测单价模拟「同一份 decode 负载摊到 k 个节点（每节点 `b → b/k`）」：

| k | 单节点 b 中位 | 单节点 tok/s | 集群合计 tok/s | 相对 k=1 |
|---:|---:|---:|---:|---:|
| 1 | 20 | 645 | 645 | 1.00x |
| 2 | 10 | 364 | 728 | 1.13x |
| **2.25** | **9** | **324** | **729** | **1.13x** |
| 4 | 5 | 182 | 730 | 1.13x |

加 2.25 倍 decode 节点只换来 **1.13 倍**集群吞吐，方程却假设了 2.25 倍。根因就是上一节的波量化：`b` 砍一半，`D` 只少 15%，每个节点付着几乎全额 step 代价却只干一半的活。所以 `T_D` 不是常数，是 `N_D` 的递减函数，配平等式在 decode 侧不成立。ISL / fresh 覆盖率还不同步（66.1% vs 75.0%），天花板配比只能报成区间 **1 : 2.25～2.55**，两个问题叠在一起，这个数更不能用。

**1 : 1.43 能用，因为它把 `T_D` 钉死在 b=32。** 1,012 是微基准单点，不随 `N_D` 变，方程自洽。附带部署约束：每个 decode 节点的并发必须维持在 32，否则配比同样失效。想加 decode 节点，必须同时把请求速率提上去，让每节点仍跑在波尾；只把现有负载摊开，上表在 k≥2 之后集群合计锁死在 ~730 tok/s，加节点几乎白加。decode 侧该做的是**集中负载而不是分散**。

**agent 负载把配比翻过来：1 : 0.74。** Prefill 空转 1,457 s（≥40.4%）是思考 / 工具往返带来的，不是引擎低效，剔不掉；decode 一条请求一旦进来就连续跑到结束，没有对应的空转。prefill 用「剔杂活、留空转」的 ≤106,124，decode 仍钉 b=32，decode 节点反而该比 prefill **少**。同一套 prefill、decode 改用本 trace 加权 644（不钉 b=32），配比是 **1 : 1.17**（`0.818 / 0.702`）——更贴近 1P1D，但 `T_D` 仍不是独立输入。空转是 c32 这条到达模式的产物：多路会话交错会填掉一部分，106,124 会往 204,892 靠；decode 若能维持 b=32，配比落在 0.74 与 1.43 之间，维持不了则落在 1.17 与 2.25 之间。选配比时，并发显著高于 c32 不要直接用 0.74。
